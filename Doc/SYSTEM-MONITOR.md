## 1. 확정 요구사항

### 1.1 공통

- 앱과 저장소는 하나다. 기능은 AI Monitor와 System Monitor로 나누고, 메뉴 막대 위젯은 각각 독립적으로 동작한다.
- 메뉴 막대 위젯은 6개다: AI Monitor, CPU, RAM, Battery, Disk, GPU.
- 위젯마다 표시/숨김을 따로 설정하고, 앱을 다시 시작해도 유지한다. 전체 System Monitor ON/OFF 스위치는 두지 않는다.
- 첫 실행(저장값 없음)에서는 AI Monitor와 CPU·RAM·Disk·Battery를 표시하고 GPU(실험적)는 숨긴다(6-9A, 2026-10-29. 이전 정책은 시스템 위젯 모두 숨김). 사용자가 저장한 ON/OFF가 항상 우선한다.
- 위젯을 클릭하면 그 위젯 전용 팝오버가 열린다.
- 숨긴 위젯은 샘플링하지 않거나 최소한으로만 샘플링한다.
- 60초 그래프 데이터는 메모리에만 두며 앱을 다시 시작하면 초기화된다.
- 샘플링 주기는 내부에서 관리하고 사용자 설정에는 노출하지 않는다.
- 수집할 수 없는 값은 `—`로 표시하고 0으로 대체하지 않는다. 시스템에 불필요한 부하를 주지 않는다.
- 메뉴 막대 위젯 순서 변경은 macOS 제약을 검증한 뒤 지원 범위를 정한다(§3 V1).
- 기존 AI Monitor 기능과 동작은 그대로 유지한다.

| GPU | `18%` 아래 `GPU` (아이콘 없음), 측정 불가 시 `—` | 최근 60초 사용률 그래프 |

- **메뉴 막대 디자인 기준 (2026-10-27 사용자 최종 결정):** 현재 AI Monitor 숫자형(`31/57` 아래 `Codex`, `51` 아래 `AGY`)과 한 세트로 보이게 한다. 숫자 아래에 이름을 두고, CPU·RAM·Disk·GPU에는 아이콘을 넣지 않는다. 기존 숫자형 렌더링 규칙을 재사용한다(§7).
- Battery는 숫자만 표시하고, 실제 충전 중이거나 외부 전원에 연결된 채 실제로 완충(원시 용량 기준)일 때만 숫자 왼쪽에 초록 번개를 붙인다(2026-10-27 사용자 최종 확정, 같은 날 6-3 실기기 확인 뒤 완충 조건 추가, §7.1 #2). **배터리 외곽 아이콘과 잔량 단계 아이콘은 어떤 상태에서도 쓰지 않는다.** 그 사이에 있었던 "상태 아이콘 + 숫자"(B안, 6-2 첫 구현)는 이 결정으로 대체되었다. 전원 연결 여부와 실제 충전 여부를 구분한다. 컬러 번개가 메뉴 막대에 실제로 표시되는지 검증한다(§3 V2).
- 배터리가 없는 Mac에서는 Battery 위젯을 비활성화하고 설정 화면에서 이유를 안내한다.
- GPU는 Apple Silicon에서 신뢰할 수 있게 수집할 수 있는지 검증한다(§3 V5). 지원할 수 없으면 임의 값을 표시하지 않고 위젯을 비활성화하며 설정 화면에서 이유를 설명한다.

#### V4 사전 검증 기록

- 저장소 밖 임시 C 하네스(`/private/tmp/tokenly_proc_probe.c`)로 `proc_listpids(PROC_ALL_PIDS)` 목록에 `proc_pid_rusage(RUSAGE_INFO_V2)`를 호출했다. 개발 셸은 788개 중 371개 성공·417개 `EPERM`(0.0066~0.0082초/순회), 현재 Debug 앱 번들 설정을 복제하고 실행 파일만 진단용으로 바꾼 임시 `.app`은 792개 중 375개 성공·417개 `EPERM`(0.0068~0.0082초/순회)이었다. 모두 UID 501이고 App Sandbox entitlement가 없었다. 시간과 프로세스 수가 다르므로 성공 PID 집합의 완전 동일성을 뜻하지는 않는다. 실제 Tokenly 바이너리 자체에 진단 코드를 삽입한 결과는 아니다.
- 성공한 PID에서 `proc_pidinfo(PROC_PIDTBSDINFO)`로 확인된 소유자는 모두 현재 사용자 UID 501이었다. 거부 PID의 소유자 정보도 같은 API에서 거부되어 소유자별 수를 산출할 수 없었다. 별도 `ps` 확인에서 PID 1 `launchd`는 root였고, 이 PID의 rusage는 `EPERM`이었다. 활동 모니터 전체 프로세스 CPU 목록에는 `WindowServer`와 `kernel_task`가 최상위에 있었지만 진단 목록에는 없었다.
- 활동 모니터 메모리 목록에서 UID 501의 Docker 가상 컴퓨터 서비스(PID 2095)는 5.89 GB, Codex Renderer(PID 72268)는 2.08 GB였다. 진단값 `ri_phys_footprint`는 각각 6028.5 MiB(5.89 GiB), 2132.4 MiB(2.08 GiB)로 가까웠다. 반면 활동 모니터 전체 목록 3위 WindowServer(약 1.15 GB)는 조회할 수 없었다. 시점·표시 단위 차이 때문에 완전한 숫자 일치 검사는 아니다.
- CPU는 두 시점의 `ri_user_time + ri_system_time` 차이를 경과 시간으로 나눈다. 이 Mac의 Mach timebase는 125/3이며 원시 CPU 시간을 나노초로 가정하면 약 41.7배 과소 계산된다. timebase 변환 뒤 단일 스레드 `yes` 부하는 2초 구간 약 100.1%였다. 활동 모니터는 갱신 시점과 구간이 달라 개별 %의 동시 일치 검증은 하지 못했다.
- 이 측정의 전체 순회는 약 2~8 ms였으며 화면 표시·타이머·Swift 객체 생성은 포함하지 않는다. App Sandbox entitlement를 임시 실행 파일에 직접 부여한 별도 시도는 정상 실행되지 않아 샌드박스가 켜진 앱에서의 성공률은 측정하지 못했다. 현재 Tokenly 앱 타깃에는 해당 entitlement가 없다. 관리자 권한 없이 전체 시스템 프로세스 TOP 5를 보장하는 방법은 확인되지 않았다.

## 4. 측정 기준 (구현된 항목)

### CPU
- `host_statistics(HOST_CPU_LOAD_INFO)`로 모든 논리 CPU를 합한 누적 tick을 읽는다.
- 사용률 = (Δuser + Δnice + Δsystem) ÷ (그 합 + Δidle) × 100, 0~100으로 제한한다.
- 최초 샘플은 `awaitingBaseline`이다.
- 카운터가 줄어들면(재설정 또는 32비트 랩어라운드) `counterReset`으로 그 구간을 건너뛰고 기준을 새로 잡는다.
- Δ합이 0이면 `noElapsedTicks`다.
- **[확인] tick 카운터는 일정하게 오르지 않는다 (2026-10-27, Mac16,12 / macOS 27, 10코어).**
  - 5 ms 간격으로 10초 관찰했을 때 갱신은 61회였다. 갱신 사이 간격의 중앙값은 6 ms였지만 최대 993 ms 동안 네 카운터가 모두 멈춰 있었다.
  - 그래서 200 ms 간격 150회 중 65회, 900 ms 간격 60회 중 2회, 1000 ms 간격 30회 중 0회가 `noElapsedTicks`였다.
  - [추정] 커널이 CPU별 tick을 모아서 반영하는 시점 때문으로 보이지만, 메커니즘은 확인하지 않았다.
  - 영향: 1초 Store 측정에서도 타이머 간격이 1초보다 짧아지면 가끔 CPU 값이 빈 구간이 생길 수 있다. UI 단계에서 표시 정책을 정해야 한다(§2.2).
- 값은 직전 샘플 이후의 평균이므로 Sampler 인스턴스 하나를 여러 소비자가 공유하면 안 된다.

### RAM
- used = App + Wired + Compressed
  - App = `internal_page_count` − `purgeable_count`
  - Wired = `wire_count`
  - Compressed = `compressor_page_count`
- Cached Files = `external_page_count` + `purgeable_count`. used에는 포함하지 않는다.
- total은 `physicalMemory`, 페이지 크기는 `host_page_size`에서 가져온다.
- 활동 모니터 "사용된 메모리"와 같은 구성이지만 측정 시점과 반올림 때문에 차이가 날 수 있다. 스왑은 포함하지 않는다.
- 이상값(total 0, page size 0, purgeable > internal, used > total, 오버플로)은 `inconsistentValues`다.

- 키가 없거나 타입이 맞지 않으면 `unsupported`, 범위를 벗어나면 `inconsistentValues`다.
- 최상위 `MaxCapacity`는 Apple Silicon에서는 %, Intel에서는 mAh라서 사용하지 않는다.
- (2026-10-28 6-4f 구현) 온도: 서비스 본체에는 없고 자식 `AppleSmartBatteryPack`의 `BatteryData.Temperature`(÷100 °C)에서 읽는다(§7.7-5, 정확도 미검증). 팩 자식이 없거나 둘 이상이면 `unsupported`.
- 시스템 정보 앱의 "최대 용량"(99%)은 레지스트리 값으로 재현되지 않는다. 그래서 건강도는 "추정치"로 표시한다.
- 최상위 키 대체 경로와 배터리 없는 Mac은 실기기로 확인하지 못했다(테스트 입력으로만 검증).

### Battery 실시간 상태 (IOPowerSources, 공개 API)

- `IOPSCopyPowerSourcesInfo` → `IOPSCopyPowerSourcesList` → `IOPSGetPowerSourceDescription`에서 `Type == InternalBattery`인 항목을 사용한다.
- 잔량 = `Current Capacity` ÷ `Max Capacity` × 100, 반올림(`pmset`과 같은 값).
- 외부 전원 연결 = `Power Source State`가 "AC Power"이면 true, "Battery Power"이면 false, 그 외에는 `unsupported`.
- 충전 중 = `Is Charging`(CFBoolean만 인정).
- 연결과 충전은 별개다. AC 연결 상태에서도 완충, 최적화 충전, 충전 제한 때문에 충전하지 않을 수 있다.
- 판정 규칙
  - internal battery 항목이 없거나 `Is Present = false`이면 `noBattery`
  - API가 아무것도 반환하지 않으면 `readFailed`
  - 값이 없거나 타입이 맞지 않으면 `unsupported`
  - current > max, max ≤ 0, current < 0이면 `inconsistentValues`

### Store 측정 정책 (3-1)

- **CPU·RAM**
  - 하나의 1초 타이머와 하나의 `MachSystemSampler`를 공유한다. 둘 중 하나라도 켜져 있으면 동작하고, 둘 다 꺼지면 타이머를 취소하고 Sampler를 버린다.
  - 다시 켜면 새 Sampler를 만든다. 그래서 첫 CPU 값은 `awaitingBaseline`이고, 멈춰 있던 구간을 평균하지 않는다.

### 상위 프로세스 측정 (3-2)

- `proc_listpids(PROC_ALL_PIDS)`로 후보 PID를 얻고 `proc_pid_rusage(RUSAGE_INFO_V2)`에 성공한 프로세스만 정렬한다. 권한 거부(`EPERM`/`EACCES`)와 종료·기타 조회 실패는 순위에서 제외하며 0으로 채우지 않는다. 조회 범위는 전체 시스템이 아닌 **현재 권한으로 조회 가능한 프로세스**다.
- CPU는 동일 PID와 동일 `ri_proc_start_abstime`의 두 시점에서 `ri_user_time + ri_system_time` 차이를 구한다. Mach tick 차이에 `mach_timebase_info.numer/denom`을 적용한 뒤 단조 경과 시간(`CLOCK_UPTIME_RAW`)으로 나눠 논리 코어 하나 기준 %를 얻는다. 멀티코어 값은 100%를 넘을 수 있다. 최초 읽기·PID 재사용·카운터 감소·경과 시간 0은 CPU 순위에서 제외한다.
- RAM은 `ri_phys_footprint` 바이트를 사용한다. CPU 기준값이 없어도 첫 읽기부터 RAM 순위를 만든다. 최대 5개만 반환하고, 5개 미만이면 실제 개수만 반환한다.
- 독립 `ProcessTopStore`는 `setVisible("cpu"/"memory", Bool)`로 팝오버 열림 상태를 받도록 준비했다. 하나라도 열리면 즉시 한 번 읽고 **3초**마다 반복하며, 둘 다 닫히면 타이머·기준값·현재 순위를 버린다. 함께 열려도 타이머 하나와 Sampler 하나만 사용하고 이전 조회가 끝나기 전에는 중복 조회하지 않는다. 3초는 2~5초 요구 범위의 중앙값이며, 임시 앱에서 전체 순회가 약 2~4 ms였으므로 1초 시스템 그래프와 별도 주기로 둔다. 실제 팝오버 연결은 6단계다.
- (3-2 안정화) 결과는 `SystemMetric<ProcessTopSnapshot>`이다.
  - 프로세스 목록(`proc_listpids`) 크기 조회나 목록 조회가 0 이하를 반환하면 `.unavailable(.readFailed(errno))`, 즉 "조회 불가"다. 호출한 앱 자신은 항상 목록에 있으므로 0 이하는 실패로 본다.
  - 목록 조회는 성공했지만 읽을 수 있는 프로세스가 없으면 `.available`이고 `readableCount == 0`, 즉 "목록 없음"이다.
  - 조회에 실패해도 CPU 기준값은 유지하므로, 다음 성공 시 실패 구간까지 포함한 사용률을 계산한다. 권한 거부와 개별 PID 실패를 제외하는 기존 정책은 그대로다.
- (3-2 안정화) 취소
  - 수집 중지(두 팝오버 모두 닫힘) 시 타이머와 진행 중인 Task를 함께 취소한다.
  - Sampler는 읽기 전후에 취소를 확인하고, 순회는 PID 64개마다 확인한다. 읽기 도중 취소되면 그 결과를 기준값으로 쓰지 않는다.
  - 완료 처리는 같은 세대일 때만 Store 상태를 바꾼다. 그래서 늦게 끝난 이전 수집은 결과를 게시하지도, 새 수집의 핸들을 지우지도 못한다.
  - 다시 열면 이전 수집을 기다리지 않고 새 수집을 즉시 시작한다. 이전 3-2 동작은 이전 수집이 끝날 때까지 새 수집을 미뤘다.
- UI 제목은 `조회 가능한 프로세스 TOP 5`, 안내는 `macOS 권한으로 일부 시스템·다른 사용자 프로세스는 제외될 수 있습니다.`로 고정했다.
- 실제 앱 설정을 복제한 임시 `.app`에 동일 Sampler 소스를 넣어 실행한 결과: 816개 안팎 중 조회 성공 423·권한 거부 393, CPU 예시 Terminal 22.6%, siriknowledged 12.6%, RAM 예시 가상 컴퓨터 서비스 6028 MiB, Codex Renderer 2107 MiB. 10회 순회는 1.7~3.5 ms였다. 실행 당시의 순간값이며 팝오버 UI·장시간 부하는 포함되지 않는다.
- **Battery**
  - 전원 알림(`IOPSNotificationCreateRunLoopSource`)이 오면 다시 읽고, 알림을 놓칠 경우에 대비해 60초 간격으로도 확인한다.
  - 근거: 잔량·전원·충전 상태는 몇 분 단위로 바뀌고, 플러그 연결·분리는 즉시 알림으로 반영된다. 매초 확인할 필요가 없다. 레지스트리 읽기 1회가 약 165 µs라서 60초 간격이면 부하를 무시할 수 있다.
  - 사이클·용량은 거의 바뀌지 않으므로 같은 시점에 함께 읽는다.
- **타이머**
  - 허용 오차 10%로 macOS가 깨우는 시점을 합칠 수 있게 하고, RunLoop common 모드에 등록한다.
- **중복과 늦은 결과**
  - 이미 켜진 지표를 다시 켜도 아무 일도 하지 않는다.
  - 이전 측정이 진행 중이면 새 측정을 시작하지 않는다.
  - 비활성화나 재시작 뒤에 도착한 결과는 세대 번호로 걸러 버린다.
- **값과 기록**
  - `nil`은 측정하지 않음(비활성 또는 첫 측정 전)이다. 측정 실패는 `readFailed`이고, 기록에는 `nil` 간격으로 남긴다. 0으로 채우지 않는다.
  - CPU의 기준값 샘플은 기록에 넣지 않는다.
- **60초 기록**
  - 메모리에만 둔다.
  - 최신 시점보다 60초 이상 오래된 점은 지우고, 최대 60개로 제한한다.
  - 시계가 뒤로 가면 기록을 초기화한다.
  - 지표를 끄면 현재값과 기록을 지운다.

### Disk (4)

- **기준:** 시스템 볼륨 `/`가 속한 APFS 컨테이너. 외장 디스크나 개별 볼륨 목록은 다루지 않는다.
- **값의 정의**
  - 전체 = `volumeTotalCapacity`
  - 사용 가능 = `volumeAvailableCapacity`(보수적 기준. macOS가 무엇을 지우기 전에 지금 비어 있는 공간)
  - 사용 = 전체 − 사용 가능. macOS가 필요할 때 지울 수 있는 데이터도 "사용"에 들어간다.
  - 사용률 = 사용 ÷ 전체
- **중요한 용도 기준 가용 값:** `availableForImportantUsageBytes`(`volumeAvailableCapacityForImportantUsage`)로 따로 제공한다. 삭제 가능한 데이터를 비워 얻는 공간이 포함될 수 있는 시스템 추정치이며, 보수적 기준과의 차이가 정확한 purgeable 총량은 아니다.
- **모델의 기본값을 보수적 기준으로 둔 이유**
  - `statfs`, `df`, `diskutil`, 시스템 정보, Finder AppleScript 다섯 곳과 일치해 검증할 수 있다.
  - 지금 바로 쓸 수 있는 공간을 보여 준다.
  - 중요한 용도 기준 값은 읽기 비용이 약 4 ms로 크다.
- **6단계 표시 기준 (2026-10-27 확정, §7.5)**
  - 메뉴 막대 사용률은 **시스템 설정 기준**, 즉 중요한 용도 기준 가용 값(시스템 설정 > 저장 공간 65.66 GB와 가까움)으로 계산한다. 값이 없으면 `—`이고 보수적 기준으로 대체하지 않는다.
  - 팝오버는 시스템 설정 기준과 **보수적 기준**(지금 실제로 비어 있는 공간)을 함께 보여 준다.
  - 두 기준의 차이는 크다(2026-10-27 실측 사용률 73.3% 대 78.8%). 모델의 `usedFraction`은 보수적 기준이므로 메뉴 막대에 쓰지 않는다.
- **판정 규칙**
  - 읽기 실패: `readFailed`(POSIX 오류 코드, 없으면 `EIO`)
  - 키 없음: `unsupported`
  - 전체 ≤ 0, 사용 가능 < 0, 사용 가능 > 전체: `inconsistentValues`
  - 사용 가능 0(가득 참)은 실제 값 0이다.
  - 중요한 용도 기준 값의 이상은 그 필드만 측정 불가로 하고, 주요 값은 유지한다.
- **표시 규칙 (UI 단계에서 적용)**
  - 용량은 Finder와 같은 10진 단위(1 GB = 10⁹ 바이트). `ByteCountFormatter`의 `.file` 스타일이 Finder·시스템 정보와 같은 "245.11 GB", "52.19 GB"를 만든다.
  - 사용률은 메뉴 막대에서 정수 %로 반올림한다(`.rounded()`, 0.5는 올림).
  - GiB(2³⁰)는 쓰지 않는다.
- **측정 주기:** 켤 때 즉시 한 번, 이후 60초마다 읽는다.
- **끌 때 보장하는 것:** 타이머를 멈추고, 진행 중인 Task에 취소를 **요청**하고, 값을 지운다.
  - 이미 시작된 동기 API 호출(`resourceValues`)은 중간에 멈추지 않고 끝까지 실행될 수 있다.
  - 보장하는 것은 그 결과를 세대 검사로 버린다는 것이다. 즉시 중단은 보장하지 않는다.
  - 근거: 용량은 분 단위로 변하므로 매초 읽을 이유가 없다. 1분이면 큰 다운로드도 늦지 않게 반영된다. 읽기 1회가 약 4 ms라 메인 스레드 밖(nonisolated async)에서 읽는다.
  - 중복 측정 방지와 늦은 결과 폐기는 CPU·RAM과 같은 세대 방식이다.
- **실측 (2026-10-27):** 전체 245.11 GB, 사용 가능 51.85 GB, 사용 193.26 GB(78.8%). 중요한 용도 기준 가용은 65.55 GB(그 기준이면 사용률 73.3%). 시스템 정보 Free 51.85 GB와 일치했다. 첫 호출은 31.5 ms(초기화 포함)였다.

### GPU (5, 실험적)

- **출처:** `IOAccelerator` → `PerformanceStatistics` → `Device Utilization %`
  - Apple이 **문서화하지 않은 키**다. 다른 기종이나 macOS에서 없거나 의미가 다를 수 있다. 코드 주석(`GPUReading`)에도 명시했다.
  - 게시 값은 "**실험적 추정 사용률**"이다. 정확한 시스템 전체 GPU 사용률을 보장하지 않는다.
- **읽기 판정 (`GPUReading`)**

  | 결과 | 의미 | 처리 |
  |---|---|---|
  | `utilization` | 정수 CFNumber 0~100 | 사용률 |
  | `notAppleSilicon` | arm64가 아님. Intel은 검증하지 않아 읽지 않는다 | `unsupported` |
  | `noAccelerator` | 서비스 없음 | `unsupported` |
  | `multipleAccelerators(n)` | 서비스가 여러 개. 선택 근거가 없어 어느 것도 쓰지 않는다 | `unsupported` |
  | `noStatistics` | 통계 속성 없음 | `unsupported` |
  | `noUtilizationKey` | 키 없음 | `unsupported` |
  | `invalidType` | Bool, 문자열, 실수, 사전이 아닌 통계 | `inconsistentValues` |
  | `outOfRange` | 범위 밖. 잘라 넣지 않는다 | `inconsistentValues` |
  | `readFailed(code)` | `IOServiceGetMatchingServices` 실패 | `readFailed` |

  - (최적화 후) 서비스 핸들을 캐시한다. 규칙은 아래 "서비스 핸들 재사용"에 있다. 최적화 전에는 매 읽기마다 서비스를 다시 찾고 해제했다.
- **지원 여부 확인:** `GPUSampler().supportStatus()`는 측정을 켜지 않고 한 번만 읽는다. `.utilization`이면 지원, 그 외는 지원하지 않는 이유다(설정 화면 안내용).
- **샘플링 정책 (aliasing 대응)**
  - 1초 창을 약 100 ms 슬롯 10개로 나누고, 슬롯마다 한 번 읽는다(one-shot 타이머).
  - 슬롯 안 읽기 시각은 시드 기반 의사난수(SplitMix64)로 정한 오프셋이다. 슬롯 경계에서 5 ms 떨어진 범위 안에 둔다. 시드를 고정하면 테스트에서 같은 시각이 재현된다(`GPUSampleSchedule`).
  - 각 읽기는 측정 시각과 결과를 함께 저장한다. 시각은 **IOKit 읽기를 시작한 시각**(호출 직전, 단조 시계 `CLOCK_MONOTONIC_RAW`, 잠자기 중에도 흐름)이다. 창 종료 시각에 정확히 시작한 읽기는 다음 창에 속한다.
  - 다음 읽기 시각은 창의 격자에서 계산한다. 그래서 타이머가 늦어도 이후 읽기가 밀리지 않는다.
- **1초 평균:** 창이 닫힐 때(다음 창의 첫 읽기 시점) 유효 읽기 평균을 게시한다.
  - 유효 5개 미만이면 `insufficientSamples`다. 모든 읽기가 같은 사유로 실패하면 그 사유를 그대로 쓴다(예: 서비스 없음 → `unsupported`).
  - 실패한 읽기는 0으로 세지 않는다. 계산은 Double로 하고, 반올림은 표시할 때만 한다.
  - 화면 값(`@Published`)은 1초에 한 번만 갱신한다. 60초 기록은 `SystemMetricHistory`이며 측정 불가는 빈칸이다.
- **오래된 창 폐기 (안정화 후)** — `GPUUtilizationWindow.isFresh(closingAt:)`
  - 창을 닫는 읽기가 다음 둘 중 하나에 해당하면, 그 창을 게시하지 않고 버린다.
    1. 창 종료 후 **0.25초**보다 늦다.
    2. 마지막 유효 읽기가 **0.75초**보다 오래됐다.
  - 버리면 현재값을 `.unavailable(.insufficientSamples)`로 바꾸고, 그 시각에서 새 창(새 위상)을 시작한다. 1~2초 지연, 긴 공백, 잠자기가 모두 이 규칙으로 처리된다.
  - **기준의 근거**
    - 0.25초: 정상적인 닫는 읽기는 종료 후 5~95 ms(다음 창 슬롯 0의 오프셋)에 타이머 허용 오차 5 ms를 더한 시점이다. 메인 스레드 지연 여유를 두었다.
    - 0.75초: 닫는 읽기가 0.25초를 다 써도, 마지막 유효 읽기가 창 후반부(0.5초 이후)에 있어야 한다는 뜻이다. 처음 시도한 0.5초는 끝의 몇 번이 실패한 정상 창까지 버려서 완화했다.
  - **수정 전 문제 (Codex 리뷰 Medium):** 창이 끝난 뒤 1초 미만이면 무조건 게시했다. 그래서 창 시작 1.9초 뒤에 재개되면 약 1초 전 데이터가 현재값으로 게시됐다. 1초 이상이면 버렸지만 현재값을 `nil`로 했다.
- **끄기·재시작:** 끄면 대기 중인 one-shot을 취소하고, 세대 번호를 올리고, 현재값·기록·부분 창을 지우고, Sampler의 `reset()`으로 캐시한 핸들을 놓는다. 다시 켜면 그 시각에서 새 창을 시작한다. 읽기는 동기 호출이라 늦게 도착하는 비동기 결과는 없다.
- **[확인] aliasing 시뮬레이션** (`GPUSampleScheduleTests`, 시드 2026, 50 ms/50 ms 주기 부하 60초)
  - 고정 위상: 모든 1초 구간이 100%로 읽혔다.
  - 시각 분산: 1분 평균 51.0%. 다만 1초 값은 20~90%(표준편차 15.5)로 흩어졌다.
  - 분산은 위상 고정에 따른 치우침을 없애지만, 1초에 10번만 읽는 데서 오는 1초 단위 잡음은 남는다.
- **[확인] 실제 앱 비용** (실제 Store·타이머·IOKit, 저장소 밖 측정 프로그램, 2026-10-27 15:52~15:56). 원본 출력·조건·프로그램 소스는 `Doc/logs/2026-10-27-gpu-cost.txt`에 있다.

  | 실행 | 시간 | 프로세스 CPU | `top` idle wakeups(정정값) | `top` 전력(상대값) |
  |---|---|---|---|---|
  | B1 GPU 끔 | 60초 | ≈0% (0.001%) | 0/s | 0.00 |
  | B1 GPU 켬, 실제 읽기 | 60초 | 0.50% | 약 4.3/s | 0.6 안팎 |
  | B2 GPU 켬, 가짜 Sampler(스케줄링만) | 30초 | 0.19% | 약 2.8/s | 0.3 안팎 |
  | B2 GPU 켬, 실제 읽기 | 30초 | 0.51% | 약 3.4/s | 0.6 안팎 |

  - B1과 B2는 서로 다른 실행 묶음이다. 실행 시간이 다르므로 같은 묶음 안에서만 비교한다.
  - **idle wakeups 정정:** 처음에는 29.3/s(B1 켬), 10.2/s(B2 가짜), 9.8/s(B2 실제)로 기록했다. 이는 잘못된 계산이었다.
    - `top`의 IDLEW 열은 초당 값이 아니라 프로세스 시작 이후의 누적 카운터다("41+", "52+", …처럼 커진다). 그런데 누적값들의 평균을 4초로 나눴다.
    - 위 정정값은 첫·마지막 기록의 차이를 경과 시간으로 나눈 대략값이다. 관찰 구간이 16~36초로 짧다.
    - 이 프로세스의 값일 뿐, 시스템 전체의 초당 깨어남 횟수와 같다고 보지 않는다.
    - 타이머는 초당 10회 울리는데 3~4/s인 이유는 확인하지 않았다([추정] 다른 깨어남과 합쳐짐).
  - **단일 읽기 비용**(같은 프로그램으로 2회 측정, 15:55~15:56과 16:08)
    - 연속 반복: 45 µs → 19 µs로 실행마다 크게 달랐다(5단계 검증 측정에서는 39~42 µs). 그래서 "수십 µs"로만 쓴다.
    - 100 ms 간격으로 따로 읽기: 약 290~350 µs로 세 번 모두 비슷했다(현재 방식 288~350 µs, 서비스 탐색만 116~146 µs, 캐시한 서비스로 속성 읽기만 209~210 µs).
  - **단일 읽기 수십 µs와 실제 앱의 장시간 CPU 비용은 별개다.** 실측은 같은 앱의 CPU·RAM·Battery를 모두 켠 비용(0.048%, §3 V7)의 약 10배다.
- **[추정] 배터리 영향:** 측정하지 않았다. 위젯이 메뉴 막대에 계속 보이면 이 비용이 하루 종일 발생한다.
- **비용 완화 대안**
  1. **(적용, B안)** 서비스 핸들 재사용. 아래 참고.
  2. (미적용) 초당 읽기 수를 줄인다(예: 5회, 최소 유효 3회). 1초 값의 잡음이 커진다.
  3. (미적용) 메뉴 막대는 낮은 빈도로, 팝오버가 열렸을 때만 초당 10회로 읽는다.
- **서비스 핸들 재사용 (B안, `GPUSampler`)**
  - IOKit 호출은 `GPURegistryAccess` 프로토콜로 분리했다(실제 `LiveGPURegistry`, 테스트용 가짜).
  - 통계에 사용률 키가 있는 서비스를 캐시한다. 값이 이상해도 서비스는 응답하므로 캐시한다(최종 안정화에서 변경, 아래).
  - 캐시한 핸들은 이 객체가 소유하며, 무효화·`reset()`·deinit 중 한 번만 해제한다.
  - 다음 경우 다시 찾아 재검증한다: 10초마다, 그리고 2초 넘게 읽지 않았을 때(잠자기, 중지 후 재개, 서비스 교체 대비).
  - **오류 종류별 재시도 정책 (최종 안정화, `GPUSampler` 주석에 명시)**

    | 분류 | 해당 결과 | 처리 |
    |---|---|---|
    | 값 이상 | 응답하는 서비스의 `invalidType`·`outOfRange` | 핸들 유지, 대기 없음. 다음 슬롯(약 100 ms 뒤)에 다시 읽는다. 처음 찾을 때 나와도 캐시한다. |
    | 서비스 소실 | 캐시한 서비스의 통계·키가 없어짐 | 핸들 해제 후 즉시 다시 찾고, 그 결과의 분류를 따른다. |
    | 일시 실패 | `readFailed`(IOKit 탐색 호출 실패) | 0.25 → 0.5 → 1 → 2초(상한)로 늘린다. 성공하거나 `reset()`하면 0.25초부터 다시 센다. |
    | 지원 불가 | 서비스 없음, 서비스 여러 개, 통계 없음, 키 없음 | 5초 대기. Mac의 특성이라 자주 찾아도 결과가 같다. |

    - 대기 중의 읽기는 직전 실패 사유를 IOKit 호출 없이 돌려준다. 이 읽기는 창에서 유효 읽기가 아니므로, 0%로 바뀌거나 오래된 값이 정상값으로 게시되지 않는다.
    - 이전 정책(최적화 직후)은 모든 실패에 5초를 적용했다. 이상값 한 번이나 일시적 IOKit 오류만으로 GPU가 곧 정상이어도 최대 5초 동안 측정 불가였다(Codex 최종 리뷰 Medium).
  - 지원 불가(→ `unsupported`)와 일시 실패(→ `readFailed`)는 사유로도 구분된다.
  - **장점:** 서비스 탐색 비용(100 ms 간격 기준 1회 약 116~146 µs)이 대부분의 읽기에서 사라진다.
  - **단점:** 상태(핸들, 시각, 재시도 시각, 일시 실패 횟수)가 생긴다. 서비스가 바뀌면 다음 재검증(최대 10초) 전까지는 이전 핸들이 응답할 수 있다. 값 이상이 계속되면 핸들을 유지한 채 초당 10회 읽는다(비용은 정상 읽기와 같음).
- **동시 접근 계약 (최종 안정화)**
  - `GPUSampling` 프로토콜과 `GPUSampler`는 `@MainActor`다. 상태를 가진 한 인스턴스를 두 실행 문맥에서 동시에 쓰면 컴파일 오류가 난다.
  - 현재 호출 경로는 `@MainActor`인 `SystemMonitorStore`의 `readGPU()`(one-shot 타이머 → `MainActor.assumeIsolated`)와 `updateGPUJob()`의 `reset()`뿐이다.
  - Store의 `gpu:` 기본값은 init 안(메인 액터)에서 만든다.
  - `deinit`은 비격리지만, 남은 참조가 없을 때만 실행되므로 핸들 해제가 다른 접근과 겹치지 않는다.
  - Store 쪽 변경은 끌 때 `reset()`을 부르는 것뿐이다.
- **[확인] 최적화 전후 실제 비용** (같은 측정 프로그램, 30초씩 번갈아 2회, 2026-10-27 16:2x, 원본은 `Doc/logs/2026-10-27-gpu-cache-optimization.txt`)

  | | 최적화 전 | 최적화 후 |
  |---|---|---|
  | 프로세스 CPU | 0.455%, 0.437% (평균 0.446%) | 0.404%, 0.341% (평균 0.373%) |
  | GPU 읽기 | 299, 300회 | 298, 300회 |
  | idle wakeups(누적 차이) | 약 0.95, 0.83/s | 약 1.75, 0.62/s |

  - 프로세스 CPU는 약 16% 줄었다. 가짜 Sampler(0.161%)를 빼서 IOKit 몫만 보면 약 0.285% → 0.212%로 약 26% 감소다.
  - 다만 같은 버전 두 번의 차이(0.404 대 0.341)가 전후 차이와 비슷하다. 감소는 확인됐지만 크기는 대략값이다.
  - idle wakeups는 실행마다 흔들려 전후 차이를 결론 내리지 않는다.
  - 배터리 영향은 측정하지 않았다(추정만).
- **실기기 테스트의 호환성 가정 수정 (Codex 리뷰 Medium):** 이전 `testLiveReadOnThisMac`은 arm64이기만 하면 GPU 값이 반드시 읽힌다고 가정했다.
  - 지금은 지원 여부와 값의 유효성을 따로 확인한다. 읽히면 0~100인지 확인한다.
  - 검증된 환경(hw.model `Mac16,12` + macOS 27.0.1)에서만 반드시 읽혀야 한다.
  - 다른 Apple Silicon에서는 미지원 판정도 허용하고, 사유를 출력한다. 미검증 기종을 지원한다고 보지 않는다.

### 자원 관리
- `mach_host_self()`는 한 번만 얻고 `deinit`에서 해제한다.
- IOKit 서비스는 `IOObjectRelease`로 해제하고, 속성 사전은 `takeRetainedValue()`로 소유권을 한 번만 가져온다.
- 반복 측정 결과 포트 수·메모리 footprint 증가와 `leaks`가 없었다.

### 7.2 위젯 상태 동기화 계약 (Codex 리뷰 High)

다섯 위젯 각각에 대해 네 가지 상태를 **하나의 값**으로 맞춘다.
- 설정 토글
- `MenuBarExtra(isInserted:)` 바인딩
- UserDefaults 저장값
- `SystemMonitorStore.setEnabled` 측정 상태

1. **단일 소유자와 저장:** `SystemWidgetController`(`@MainActor`, `ObservableObject`, 앱에 하나, `TokenlyApp`의 `@StateObject`)가 소유한다.
   - 위젯별 "사용자가 원하는 삽입 상태"를 UserDefaults 키 `systemWidget.<cpu|memory|battery|disk|gpu>.inserted`(Bool, 없으면 false)로 저장한다.
   - 다른 곳은 이 값을 따로 저장하지 않는다.
2. **토글과 바인딩 연결:** 설정 토글과 `MenuBarExtra(isInserted:)`는 같은 `controller.binding(for: widget)`을 쓴다.
   - getter는 유효 상태(`저장값 && 지원됨`)를 돌려준다.
   - setter는 `controller.setInserted(widget, value)` 하나만 부른다.
   - 사용자가 ⌘-드래그로 아이템을 빼면 macOS가 바인딩에 false를 쓰므로, 같은 setter를 거친다(동작은 6-3에서 확인, §7.9).
3. **Store 측정 시작·중지 시점:** `setInserted`는 메인 액터에서 동기적으로 다음 순서로 실행된다.
   1. 같은 값이면 즉시 반환한다.
   2. UserDefaults에 쓴다.
   3. `@Published` 상태를 바꾼다.
   4. `store.setEnabled(metric, 유효 상태)`를 호출한다.
4. **앱 시작 시 적용:** 컨트롤러 init에서 다음 순서로 실행한다. 라벨의 `onAppear`에 의존하지 않는다(AI의 조회 시작 경로와 분리).
   1. 저장값을 읽는다.
   2. 지원 여부를 한 번 확인한다(§7.6).
   3. 유효 상태가 true인 위젯마다 `store.setEnabled(metric, true)`를 한 번 호출한다.
5. **위젯 제거:** 토글을 끄든 ⌘-드래그로 빼든 3번 경로로 `setEnabled(false)`가 호출된다.
   - Store가 그 지표의 타이머·진행 중 작업을 취소하고 값과 기록을 지운다(구현된 동작).
   - CPU·RAM 위젯이면 컨트롤러가 `processTop.setVisible("cpu"/"memory", false)`도 호출한다. 팝오버가 열린 채 제거된 경우의 안전장치다(§7.7).
6. **종료·재시작:** 변경할 때마다 바로 저장하므로 종료 시 따로 저장할 것이 없다. 재시작하면 4번으로 복원한다. 측정값과 60초 기록은 복원하지 않는다(§1.1).
7. **중복·경합·재진입 방지**
   - 모든 경로가 메인 액터 동기 호출이다(비동기 Task 없음).
   - `setInserted`의 같은 값 검사와 `setEnabled`의 멱등성으로 중복 호출은 효과가 없다.
   - SwiftUI가 뷰 갱신 중 바인딩 setter를 부를 때 "Publishing changes from within view updates" 경고가 나는지 6-3에서 확인한다. 경고가 나면 변경을 다음 메인 루프로 미루되, 실행 시점에 같은 값 검사를 다시 한다.
8. **가려짐과 제거는 구분할 수 없다:** 메뉴 막대 공간이 부족해 노치 뒤로 가려진 아이템도 `isInserted == true`로 남는다.
   - **`isInserted == true`는 실제 화면 노출을 보장하지 않는다.** 가려진 위젯은 계속 측정된다.
   - 공개 API로 가려짐을 확인하는 방법은 확인하지 못했다. 이번 단계에서는 구분하지 않고, 설정 탭에 "메뉴 막대가 가득 차면 일부 위젯이 보이지 않을 수 있음"을 안내한다.

### 7.3 기존 숫자형 렌더러 재사용

`Views/MenuBarNumericRow.swift`(AI 파일)는 수정하지 않고, 이미 `static`인 규칙을 호출한다. 새로 만드는 `MenuBarSystemImage`는 열 배치만 담당한다(`NumericGaugeItem`은 AI 서비스 종류에 묶여 있어 직접 쓸 수 없다).

| 재사용 규칙 | 값 (`Layout.standard`) | 시스템 위젯 |
|---|---|---|
| `font(_:weight:)` | SF Rounded | 모든 글자 |
| `primarySize`·`primaryWeight` | 12pt Semibold | 숫자 |
| `secondaryWeight` | Medium | `%` (숫자와 같은 기준선). 크기는 AI `secondaryRatio`(0.8) 대신 시스템 전용 `percentRatio` 0.75 |
| `separatorGap` | 1.2pt | 숫자와 `%` 잉크 사이 |
| `nameSize`·`nameWeight`·`digitsToName` | 6pt Semibold, 1.75pt | CPU·RAM·Disk·GPU 이름 |
| `vertical(layout).singleBaseline`·`.nameBaseline` | AGY와 같은 기준선 | 2단 위젯의 숫자·이름 |
| `height`·`staleAlpha` | 22pt, 0.5 | 이미지 높이, 흐린 표시 |
| `sidePadding` | 1pt | AGY 픽셀 비교 테스트에서만 사용. 시스템 위젯은 `MenuBarSystemImage.itemPadding` 0.5pt |
| 렌더 처리 | sRGB, 배율 ≥ 2, `setShouldSmoothFonts(false)`, 픽셀 스냅, `isTemplate = false`, 라이트 검정·다크 흰색 | 그대로 |

- **2단 위젯 (CPU·RAM·Disk·GPU)**
  - 열 폭은 `max(숫자 칸 폭, 이름 잉크 폭)`이다. 숫자 칸은 `10%`~`99%` 중 가장 넓은 잉크 폭(23.51pt)이고, `100%`일 때만 `100%` 잉크 폭(29.58pt)이다. 숫자는 가운데 정렬한다.
  - 이미지 폭은 `0.5pt + 열 폭 + 0.5pt`를 올림한 값이고, 올림으로 생긴 여분은 좌우에 나눈다(`left(width:)`). CPU 이미지는 32pt → 25pt가 되었고, `24%`의 좌우 빈 공간은 각 4.7pt → 1.2pt다.
  - 이유: 6-3 실기기 확인에서 시스템 위젯 사이가 AI 숫자형보다 넓어 보였다(잉크 사이 약 25pt, AI 약 16~19pt). 아이템 사이 16pt(좌우 각 8pt)는 macOS `NSStatusItem`이 정하며, 앱에서 바꾸는 공개 수단은 시스템 전체 설정(`NSStatusItemSpacing`)뿐이라 쓰지 않는다. 앱이 줄일 수 있는 것은 이미지 안쪽 여백뿐이므로 `100%` 기준 고정 폭의 빈 공간을 줄였다. 지금 잉크 사이 간격은 약 16 + 2.4 ≈ 18pt다.
  - 대가: 값이 99%↔100%를 오갈 때(예: GPU 부하) 아이템이 약 6pt 넓어졌다 좁아진다. 원래 결정(`100%` 기준 고정)으로 되돌리려면 `digitSlotWidth`가 항상 `hundredWidth`를 쓰게 하면 된다.
- **Battery (한 줄, 최종 디자인)**
  - `82%` 또는 `⚡82%`를 한 줄로 그린다. **최종 확정(사용자): 22pt 이미지 전체 높이의 세로 중앙.** 다른 위젯의 윗줄 숫자에 맞추지 않는다.
    - 숫자 `0`의 잉크(기준선 기준 −0.18 ~ 8.63pt)의 중심이 이미지 중심(11pt)에 오도록 기준선을 `centredBaseline` = 11 + 잉크 중심 = **15.23pt**로 둔다. 숫자 윗선은 위에서 6.60pt다.
    - 번개 중심도 같은 선(11pt)에 놓아, 번개만 있든 숫자만 있든 둘이 함께 있든 그룹이 세로 중앙이다. `%`는 작아도 같은 기준선이라 그룹 위치를 바꾸지 않는다.
    - 경과: 6-2는 행 가운데(기준선 15.32pt) → 6-3 1차 보완에서 2단 위젯 숫자 기준선(12.23pt)에 맞춤 → 실기기 확인 뒤 사용자가 "한 줄 위젯은 전체 높이 중앙"으로 최종 확정.
  - 숫자 글꼴과 `%` 규칙은 위와 같다(`%` 0.75배). 숫자 색은 검정·흰색이다.
  - **번개 색 (명암별):** 라이트 sRGB 0.09/0.62/0.24(흰 배경 대비 약 3.5:1), 다크 0.24/0.84/0.40(검은 배경 대비 약 11:1). 이전 시스템 초록(0.20/0.78/0.35)은 흰 배경 대비 약 2.2:1로, 밝은 배경화면에서 흐려 보였다.
  - **폭:** (번개가 보이면 번개 + 1pt) + 숫자 칸(두 자리 기준, 100%면 `100%`)이다. 0~99% 사이 갱신으로는 폭이 바뀌지 않고, 번개가 생기거나 없어질 때(전원 연결·분리, 충전 시작·끝, 완충)와 100%에서만 바뀐다. 번개 칸을 항상 비워 두면 어댑터를 뺀 평소 상태에 빈 공간이 약 7pt 생겨 이번 간격 보완과 맞지 않는다. 이미지: `82%` 25pt, `⚡82%` 33pt, `100%` 31pt, `⚡100%` 39pt(번개를 키워 충전 표시 폭이 1pt 늘었다).
  - **번개:** `bolt.fill` 13pt **Bold**를 `paletteColors`로 칠한다. 심볼 이미지에는 잉크 밖 여백이 있어 `alignmentRect`가 잉크와 맞지 않는다. 그래서 한 번 그려 잉크 영역을 측정하고 그 부분만 그린다. 잉크 높이 **11.5pt**(이전 10pt Medium, 폭 6.2 → 7.0pt), 숫자 잉크까지 간격 **1.25pt**. 숫자보다 위아래로 약 1.4pt씩 크다.
  - **간격 고정:** 번개 위치를 픽셀 스냅된 숫자의 실제 잉크 왼쪽에서 거꾸로 계산한다. 번개와 숫자를 따로 스냅하면 값에 따라 빈 간격이 1~3px로 달라졌다(테스트로 발견).
  - 값은 `MenuBarSystemImage.BatteryStyle.standard` 한 곳에 있다. `.previous`는 비교용이다.
  - 측정 전은 `—`를 흐리게, 측정 불가는 `—`를 흐리지 않게 그린다. 번개는 없다.
  - 22pt와 좌우 경계, 2×·3× 배율에서 잘리지 않는지 테스트로 검증했다.
  - 이력: 6-2 첫 구현은 "잔량 단계 아이콘 + 숫자"였다. 사용자 최종 확정으로 외곽 아이콘을 없앴다.
- **표시 방식 (통일형·구분형, 6-3 후속)**
  - `SystemWidgetLayout` (`unified`·`split`). `MenuBarSystemImage.baselines(_:)`가 숫자·이름 기준선만 바꾼다. 글꼴(숫자 12pt Semibold, `%` 0.75배 Medium, 이름 6pt Semibold), 열 폭, 가로 위치, 여백, 스냅, 색은 두 방식이 같다.
  - 통일형: AGY 열 기준선 그대로(숫자 12.23pt, 이름 19.40pt). 표시 방식 도입 전 렌더러와 픽셀이 같다(196개 조합 해시 비교, 테스트에 10개 내장).
  - 구분형: 통일형과 **같은 상자를 위아래로 뒤집고**(행 사이 빈 간격이 통일형과 같다), **묶음 전체를 2pt 위로 올린다**(`splitLift`). 1차 1pt("C안"), 같은 날 AGY·Battery 변경과 함께 비교한 뒤 1pt 더(최종 "C안", 2026-10-28). 결과: 이름 기준선 5.88pt, 숫자 기준선 17.40pt, 3× 실측 잉크 1.33–17.67pt(위 여백 1.33, 아래 여백 4.33), 세로 무게중심 10.76pt(AI 전체 10.82pt와 −0.06).
    - 이유(측정): 큰 숫자가 아래 행에 있어 알파 가중 세로 무게중심이 12.76pt로 AI(Codex 11.13, AGY 10.83)보다 1.6~1.9pt 낮았다("처져 보임"). 0.5pt 올림은 12.34, 1pt 올림은 11.76. 1pt에서 AI와 차이가 0.6~0.9pt로 줄고 22pt 안에서 잘림이 없다(224개 조합).
    - 가로 보정은 하지 않는다. 숫자·`%` 잉크 상자는 열 가운데(오프셋 0.00), 글꼴 기준 중심은 +0.1~0.25pt이고, 알파 가중 무게중심은 평균 −1.15pt(값마다 −0.30~−1.67)다. 0.5pt 여백 정책 안에서 줄 수 있는 고정 보정은 0.25pt 미만이고(100%는 0.25pt만으로 오른쪽 여백 0.33pt), 값마다 다른 치우침은 고정 보정으로 없앨 수 없다.
    - 비교 자료: `Doc/screenshots/stage6-3-split-final/`(1차 1pt 기준 통일형·구분형), `options-abc/`(A 0pt·B 0.5pt·C 1pt 비교와 측정값). 최종 2pt 비교는 저장소 밖 `../../TokenlyDesignArchive.noindex/Stage6-8C/System-Alignment/`.
- **AGY 숫자 0.5pt 올림 (6-3 최종):** `MenuBarNumericImage.Layout.singleNumberLift`(기본 0, `standard` 0.5). 7일 칸이 없는 열(현재 AGY뿐)의 숫자 기준선에서만 뺀다. 이름·Codex·Claude·열 폭·`vertical(_:)`은 그대로라 시스템 통일형(같은 `singleBaseline` 사용)도 바뀌지 않는다. 시스템 열과 AGY 열 픽셀 비교 테스트는 `singleNumberLift = 0` 레이아웃과 비교한다.
  - 측정: AGY 숫자 잉크 윗선 3.67 → 3.00pt(Codex 큰 숫자 2.67), 숫자–이름 간격 2.00 → 2.67pt, 무게중심 10.83 → 10.38pt.
- **Battery 라운드 테두리 (6-3 최종, 선택):** `BatteryFrameStyle`(`minimal` 기본·`rounded`). `MenuBarSystemImage.framed`가 미니멀 이미지를 그대로(정수 pt 오프셋 3pt, 재표본 없음) 가운데 두고 테두리만 덧그린다. 가로는 그려진 내용 잉크 + 2.25pt, 세로는 고정 높이 17.5pt(선 중심 기준, 22pt 중앙; 선 바깥 1.875–20.125pt. 처음 15.75pt에서 같은 날 조정). 선 색은 숫자색(검정·흰색) 55%, 측정 전 `—`는 함께 흐리게(×0.5). 폭: `82%` 31, `⚡82%` 39, `100%` 37, `⚡100%` 45pt.
  - 측정 전 흐림은 숫자 행에만(구분형에서는 아래 행) 적용하고 이름은 흐리게 하지 않는다.
  - Battery는 `applied(to:)`로 항상 통일형(한 줄 중앙)을 쓴다.
- **픽셀 비교 테스트가 보장하는 범위**
  - 보장한다: `%`를 끈 시스템 열(`51`/`AGY`)과 AI 렌더러의 AGY 열이 같은 폭·배율·명암에서 픽셀이 같다. 즉 숫자·이름의 글꼴, 굵기, 기준선, 스냅, 색 처리가 같다.
  - AGY 비교는 AI 여백 1pt로 그린다(`render(..., aiPadding: true)`). 시스템 위젯의 0.5pt 여백은 그 밖의 테스트(폭 규칙, 빈 공간 상한)로 검증한다.
  - 6-3 보완 테스트: CPU·RAM·Disk·GPU 숫자의 픽셀 윗선·아랫선이 AGY 숫자와 같은 행인지(2×·3×), CPU 이름 아랫선이 AGY와 같은지. Battery는 0·9·24·99·100% × 번개 없음·충전·완충 × 라이트·다크 × 2×·3×에서 진한 잉크 그룹의 세로 중심이 이미지 중심과 1px 안인지, 번개 중심이 숫자 중심과 1.5px 안인지, 번개 간격이 일정한지(차이 ≤ 1px), `%` 0.75배·기준선 일치(Battery와 CPU의 `%` 픽셀 높이 동일), 번개 크기·색 대비.
  - 보장하지 않는다: `%`의 배치 미감, 실제 메뉴 막대에서의 모습(시스템 틴트, 아이템 간격), 다른 macOS의 글꼴 렌더링. 이 항목들은 GUI 확인으로 다룬다.

### 7.6 지원 여부와 일시 실패

- **지원 여부 확인:** 컨트롤러 init에서 메인 액터로 한 번만 확인한다.
  - Battery: 별도 `BatterySampler().samplePowerState()`
  - GPU: **별도** `GPUSampler().supportStatus()`. Store의 Sampler는 쓰지 않는다.
- **위젯을 켤 수 없게 만드는 것은 영구적인 판정뿐이다.**
  - Battery: `noBattery`
  - GPU: `notAppleSilicon`·`noAccelerator`·`multipleAccelerators`·`noStatistics`·`noUtilizationKey`
  - 이때 유효 상태는 false이고 설정 토글도 꺼지며 이유를 안내한다. **저장값은 덮어쓰지 않는다.**
- **일시 실패는 지원 불가로 저장하지 않는다.** GPU `readFailed`나 이상값, Battery 읽기 실패가 여기에 해당한다. 이 경우 위젯은 켤 수 있고 값만 `—`로 보인다.
- 실제 주기 측정값은 반드시 `SystemMonitorStore`를 거쳐 UI에 전달한다. UI가 Sampler를 직접 읽지 않는다(HANDOFF "6단계 UI 연결 시 지켜야 할 GPU 제약").
- Battery 상태 구분: 첫 측정 전(`batteryPower == nil`), 배터리 없음(`noBattery`), 일시적 읽기 실패(`readFailed` 등 그 밖의 `unavailable`), 정상(`available`). 번개는 실제 충전 중이거나 외부 전원 연결 + 실제 완충일 때만 표시하고, 전원에 연결됐지만 100% 미만에서 충전하지 않으면 표시하지 않는다(§7.1 #2). VoiceOver 문구는 각각 "배터리 82%, 충전 중", "배터리 100%, 전원 연결됨"이다.

### 7.7 팝오버와 TOP 5 수명주기

- 팝오버는 기존 스타일을 따른다(폭 340, `.regularMaterial`, 여백 14, 글꼴 체계, §1.3).
  - CPU: 현재값(사용자·시스템), 60초 그래프, TOP 5
  - RAM: 사용/전체, App·Wired·Compressed·Cached Files, 60초 그래프, TOP 5
  - GPU: "실험적 추정 사용률", 60초 그래프, 비공개 키 안내
  - Battery: 잔량, 전원·충전 상태 문구, 사이클, 건강도(추정치), 최대/설계 mAh, 온도 "지원 안 함"
  - Disk: 두 기준
- **`ProcessTopStore`는 앱에 하나**만 둔다(`TokenlyApp`의 `@StateObject`).
  - CPU 팝오버는 키 `"cpu"`, RAM 팝오버는 키 `"memory"`로 `setVisible(key, true/false)`를 호출한다.
  - Store가 키 집합으로 관리하므로, 둘이 동시에 열려도 수집은 하나이고 둘 다 닫히면 멈춘다(구현된 동작).
- **1차 연결:** 팝오버 내용 뷰의 `onAppear`/`onDisappear`. **이것이 열림·닫힘을 정확히 전달한다고 가정하지 않는다.**
  - 6-4에서 아래 상황을 실제로 확인한다. 각 `setVisible` 호출과 `ProcessTopStore`의 조회 시작·중지를 UI 계층의 디버그 로그(`Logger`)로 기록하고, 닫혀 있을 때 3초 주기 조회가 없는지 확인한다.
    - 열기, 닫기
    - 빠르게 다시 열기
    - 열린 상태에서 위젯 제거
    - CPU·RAM 팝오버 사이 전환
    - 앱 종료
  - 이벤트가 빠지거나 늦으면 **대안**으로 바꾼다. 팝오버 `NSWindow`를 잡아(기존 `SettingsWindowCapture`와 같은 방식) 창이 보이는지·닫히는지를 알림으로 판단한다.
- **안전장치:** 위젯을 제거하면 컨트롤러가 해당 키를 false로 만든다(§7.2-5). 닫힌 팝오버 때문에 TOP 5 조회가 계속되는 일이 없어야 한다.
- **TOP 5 표시:** 이름과 사용량을 한 줄로 쓴다.
  - CPU는 코어 하나 기준 %(소수 1자리, 100% 초과 허용). AI 전용 0~100 제한 포맷터(`NumericGaugeItem.text`)는 쓰지 않는다.
  - RAM은 바이트 단위(`ByteCountFormatter`).
  - 제목은 "조회 가능한 프로세스 TOP 5"이고, 권한 안내 문구를 붙인다.

### 7.7-1 CPU 팝오버 (6-4b 구현, 2026-10-28)

상태: **구현 완료 · 자동 테스트 검증 완료 · 실제 앱 확인 완료(라이트·다크·시스템 전환 포함, 2026-10-28; HANDOFF 6-4b).**

- **디자인:** 미리보기 1~4차 비교 후 **B1 Original "Aurora Flow"** 채택(`../../TokenlyDesignArchive.noindex/Stage6-8C/CPU/round4-aurora/`, 저장소 밖).
- **레이아웃 (340 × 약 335pt):**
  - 글래스 카드(모서리 12pt, 위에서 옅은 민트 빛, 얇은 흰 테두리, 좌우·위 8pt): `CPU` + 부하 표시 + 톱니바퀴(설정 열기, `SettingsWindowManager`) / 큰 현재값(44pt Rounded Semibold) / 사용자·시스템 % / 그래프 84pt.
  - "프로세스 TOP 5" + ⓘ(마우스를 올리면 도움말, 누르면 아래에 펼침): 아이콘 · 이름(가운데 생략) · 코어 1개 기준 %(오른쪽 정렬, 잘리지 않음).
  - 넣지 않는 것: 60초 평균·최고, 긴 권한 설명, 측정 주기 안내, 하단 설정 링크. 도움말 내용: 프로세스 %는 코어 1개 = 100%라 100%를 넘을 수 있음, 위의 전체 %는 모든 코어 기준, 권한에 따라 일부 프로세스 제외.
- **부하 표시 (`SystemWidgetPresentation.cpuLoad`):** 반올림 전 전체 %로 40 미만 "여유", 40~80 미만 "보통", 80 이상 "높음". 글자로 표시하고 색은 그래프의 청록 하나(위험 색 아님). "위험"·"고장" 같은 표현은 쓰지 않는다.

  - 데이터: `SystemMonitorStore.cpuHistory`(실측, 1초). 오른쪽 끝 = 기록의 마지막 시각, 왼쪽 = 60초 전. 세로 0~100% 고정(위 3pt 여백, 오른쪽 7pt 여백). 자동 확대 없음.

  - 미리보기와 다른 점: 그라데이션이 위 3pt 여백까지 정확히 0~100%에 맞춰져 점 색과 선 색이 같은 값에서 일치한다(미리보기는 전체 높이 기준이라 최대 3.5% 어긋났다).
- **TOP 5 아이콘 (`ProcessIconProvider`):** PID로 `NSRunningApplication`을 찾아, `.app` 묶음이 있고 활성화 정책이 `prohibited`가 아닐 때만 그 앱 아이콘. 그 밖(WindowServer, 데몬, WebKit·Chrome 보조 프로세스)은 공통 기본 아이콘(`gearshape.2.fill`). 이름으로 추측하지 않는다. 캐시 키는 (PID, 시작 시각) — 재사용된 PID는 다시 조회하고, 목록에서 빠진 프로세스는 캐시에서 지운다. 이를 위해 `ProcessCPUEntry`에 `startTicks`를 추가했다(기존 `ProcessTopCalculator`의 같은 프로세스 판정과 같은 값).
- **수명주기:** CPU 항목만 `.menuBarExtraStyle(.window)`. 다른 위젯은 기존 임시 메뉴. 팝오버 내용의 `onAppear`/`onDisappear`와 창 가시성(`NSWindow` 가려짐 상태·닫힘 알림) 두 신호가 모두 `SystemPopoverVisibility.set`을 부른다. `ProcessTopStore.setVisible`이 키별로 멱등이라 중복 수집이 없고, 어느 한 신호만 와도 멈춘다. CPU 위젯이 꺼져 있으면 수집을 시작하지 않고, 열린 채 위젯을 끄면 컨트롤러가 멈춘다. 각 호출은 `Logger`(subsystem `io.github.jbbdyee.tokenly`, category `SystemPopover`, debug)로 남는다.
- **설정 버튼 (실기기에서 발견·수정):** 팝오버 창은 일반 창보다 높은 층(layer 101)에 떠서, 톱니바퀴로 연 설정 창이 팝오버 뒤에 가려졌다. 이제 톱니바퀴는 팝오버를 먼저 닫고(`dismiss`, 닫히지 않으면 그 창을 `orderOut`) 다음 런루프에서 설정 창을 앞으로 가져온다. 실제 앱에서 확인함(두 번 모두 팝오버가 닫히고 설정 창이 맨 앞).
- **앱 외관 설정 (앱 전체, 2026-10-28 최종):** Tokenly 앱 외관 설정(시스템 / 라이트 / 다크)은 `AppAppearanceApplier`(`TokenlyApp.swift`)가 `NSApp.appearance` 하나로 적용한다(시스템 = nil). 설정 창·AI 팝오버·CPU 팝오버 모두 여기서 외관을 받는다. `.preferredColorScheme`과 창별 `NSWindow.appearance`는 쓰지 않는다. 이유: 재현에서 `.preferredColorScheme`은 라이트 → 시스템 전환 후 어두운 창에 검은 글자를 남겼고, 창별 `NSWindow.appearance`는 SwiftUI가 덮어써 창(다크)과 글자색(라이트)이 어긋났다. 메뉴 막대 라벨은 앱 외관과 관계없이 메뉴 막대를 따른다(재현에서 확인). 실제 앱에서 반복 전환을 확인했다(HANDOFF 6-4b).
- **프로세스 이름 잘림:** 6-4c에서 해결(§7.7-2 "프로세스 이름 전체 수집"). 31자로 꽉 찬 이름은 실행 파일 이름으로 보완하고, 이름 칸에 마우스를 올리면 전체 이름이 보인다.

### 7.7-2 RAM 팝오버 (6-4c, 2026-10-28)

상태: **구현 완료 · 자동 테스트 통과(354) · 실제 앱 검증 완료(다크·라이트·시스템 전환, 아래 HANDOFF 6-4c).** 아래 "미리보기" 항목은 승인 전 기록으로 남긴다.

- **구현 (`SystemMonitor/UI/RAMPopoverView.swift`):** 승인된 미리보기 그대로. CPU 팝오버의 카드·B1 `AuroraGraph`(`store.memoryHistory`)·`ProcessIconView`·`SystemPopoverVisibility`(키 `"memory"`)·`WindowVisibilityReporter`·설정 버튼(팝오버 닫고 설정 창 앞으로)을 재사용. - **구성 막대 계산 (`SystemWidgetPresentation.memoryComposition`):** 앱(익명 − 퍼지 가능) · 와이어드 · 압축(압축기가 차지한 페이지)은 겹치지 않는 물리 페이지이고 합이 `usedBytes`(사용률과 같은 값). 사용 가능 = `totalBytes − usedBytes`. 네 칸 합 = 전체(테스트·실측 검산). 칸 너비는 정확한 비율(0이 아닌 칸은 최소 3pt). "사용 가능" ⓘ: 비어 있는 메모리와 캐시된 파일처럼 macOS가 바로 내줄 수 있는 메모리 포함.
- **메모리 압박 (`MemoryPressure`, `SystemMonitorStore.memoryPressure`):** RAM 샘플마다(1초, RAM이 켜져 있을 때만) `sysctlbyname("kern.memorystatus_vm_pressure_level")` 1회(약 2µs). 값은 공개 `DispatchSource.MemoryPressureEvent`와 같음: 1 정상 → "정상", 2 → "주의", 4 → "높음". 다른 값은 `inconsistentValues`, 읽기 실패는 `readFailed(errno)` → "확인 불가"(정상으로 추정하지 않음). 로그 없음. 사용률 값과 독립(실패해도 `memory`는 그대로). RAM을 끄면 지움.
- **TOP 5:** `phys_footprint` 내림차순 5개(`memoryTopRows`), MB/GB. ⓘ: 프로세스별 값의 합은 위의 사용량과 같지 않음. 아이콘 캐시는 CPU와 공유(두 목록의 키를 함께 유지).
- **프로세스 이름 전체 수집 (`ProcessNames.full`, `LiveProcessReader.executableName`):** 커널 `pbi_name`(최대 31자)이 꽉 찬 이름만 `proc_pidpath`의 실행 파일 이름을 읽고, 그것이 보고된 이름으로 시작할 때만 바꾼다(다른 실행 파일로 이름을 바꾸지 않음). 예: "com.apple.Virtualization.Virtua" → "com.apple.Virtualization.VirtualMachine". UI는 폭이 모자랄 때만 가운데 생략, 마우스를 올리면 전체 이름(CPU 팝오버에도 같은 툴팁 추가).

- **압박 배지 색 (2026-10-28 추가, 구현·테스트·실제 앱 확인):** `RAMPopoverView.pressureBadge`. 상태별 글자/배경 — 다크: 정상 `#A5E2D7`/`#254A46`, 주의 `#F4D39A`/`#53452F`, 높음 `#F2B1C4`/`#593A46`, 확인 불가 `#C1C4CD`/`#41444B`. 라이트(같은 파스텔 계열, 글자 대비 ≥ 4.5:1): 정상 `#1F6B5E`/`#D9F2EC`, 주의 `#7A5212`/`#FAEBCF`, 높음 `#8E3553`/`#F8DEE6`, 확인 불가 `#4E525B`/`#E6E7EB`. 색은 실제 압박 값만 따르고(사용률로 추정 안 함), 문구도 함께 바뀐다. 크기·위치는 그대로.

### 7.7-4 Disk 팝오버 (6-4e)

상태: **구현 완료 · 자동 테스트 통과(전체 376개 통과 후 경계 테스트 1개 추가, 표기 수정 뒤에는 Disk 관련 21개만 재실행) · Debug·Release 빌드 성공 · 실제 앱 검증 완료**(2026-10-28: Claude가 실행·메뉴 막대 값·재실행 복원·실제 CPU를, 사용자가 팝오버 76% 일치·구성 막대·줄무늬·장치 줄·실시간 그래프·도움말·톱니바퀴·테마 전환을 확인). 이후 작은 속도 표기를 "0.1 MB/s 미만" → "<0.1 MB/s"로 바꿨다(읽기·쓰기 공통 포맷터, 실제 0은 "0 MB/s", 실패는 "확인 불가" 그대로). 승인 디자인 B안 + P1 아쿠아·민트. 아래 "조사 기록"은 승인 전 내용이다.

- **화면 (`SystemMonitor/UI/DiskPopoverView.swift`):** `Disk` + 톱니바퀴 / 큰 % + "N GB 사용"·"전체 N GB" / 구성 막대(사용 중 · 필요 시 확보 가능 (추정, 줄무늬) · 지금 비어 있음) / 범례 3줄 + 구분선 + "사용 가능" / ⓘ(마우스를 올리면 도움말, 누르면 펼침, 기본은 접힘) / 장치 줄 / "디스크 활동 · 최근 60초" 읽기·쓰기 두 그래프. 폭 340, 카드·글꼴·톱니바퀴 동작은 CPU·RAM·GPU와 같음. 장치 줄은 다크에서 승인 시안(tertiary)보다 약간 밝게(`primary` 42%). Disk 항목만 `.menuBarExtraStyle(.window)`로 바꿨다.
- **용량 (`DiskSpaceBreakdown`):** 기존 `DiskUsage` 한 번의 읽기(같은 컨테이너, 같은 시점)에서 사용 중 = 전체 − 사용 가능, 확보 가능(추정) = 사용 가능 − 지금 비어 있음, 지금 비어 있음 = `availableBytes`. 세 값의 합 = 전체(바이트 단위로 정확히). 막대 폭은 바이트 비율. 사용 가능 추정치가 없거나 지금 비어 있음보다 작거나 전체보다 크면 구성은 "—"(막대 비움). 큰 숫자는 `SystemWidgetPresentation.disk`를 그대로 써서 메뉴 막대와 같다. 표시는 10진 단위(1 GB = 10⁹ B, 1 TB 이상은 TB). 로컬 스냅샷 크기는 추측하지 않는다.
- **읽기·쓰기 수집 (`DiskActivitySampler`, actor):** `/`의 BSD 장치(`statfs` f_mntfromname)에서 IORegistry 서비스 평면을 위로 따라가 `IOBlockStorageDriver`를 찾는다(이 Mac: APFS 스냅샷 → 볼륨 → 컨테이너 → `disk0s2` → `disk0` → 드라이버). 각 단계의 부모가 정확히 1개여야 하고(여러 물리 저장소·모호함 → `unsupported`), 드라이버의 장치가 `Virtual Interface`면(디스크 이미지) 거부, `Statistics`에 두 바이트 키가 있어야 한다. 이름 문자열이나 "첫 번째 내장 디스크"에 기대지 않는다. 찾은 드라이버는 레지스트리 ID로 캐시하고, 읽기에 실패하면 다음 읽기에서 다시 찾는다(ID가 바뀌면 새 기준값). 볼륨 이름·파일 시스템은 1회, 내장 여부(`Physical Interconnect Location`)·SSD(`Medium Type`)는 찾을 때 1회. 모델·일련번호는 읽지 않는다.
- **속도 (`DiskActivityRateTracker`):** (바이트 증가량) ÷ (실제 경과 시간, `CLOCK_MONOTONIC` — 잠자기 중에도 흐름). 1 MB = 10⁶ B. 처음·실패 후·다른 장치 → `awaitingBaseline`(점 없음), 경과 ≤ 0 → `noElapsedTicks`, 경과 > 2.5초(잠자기·지연) → 새 기준값(점 없음), 누적값 감소 → `counterReset`, 100 GB/s 초과 → `inconsistentValues`, 읽기 실패 → 그 사유. 성공이 아닌 결과 뒤에는 항상 새 기준값이라 공백을 가로지르는 평균이 없다. 장치 선택 실패(`unsupported`, 화면 "확인 불가")와 실제 0 MB/s("0 MB/s")는 다르다.
- **수명주기 (`SystemMonitorStore`):** Disk 위젯이 켜져 있는 동안 1초 작업 하나(`diskActivityInterval`), 켤 때 즉시 1회. 용량은 그대로 60초. 진행 중 읽기가 있으면 그 틱은 건너뛴다(중복 Task 없음). 끄면 두 작업 취소, 추적기·기록·장치 정보 삭제, 늦게 도착한 결과 폐기(`diskGeneration`). 팝오버는 새 수집을 만들지 않고 저장소를 관찰만 한다. 기록은 `SystemMetricHistory`(60초, 최대 60점).
- **그래프:** 읽기·쓰기 각자 색(P1 읽기 `#9FE3E6`/`#1F8A96`, 쓰기 `#B2E8C8`/`#2E9467`, 사용 막대 아쿠아 → 블루 `#A7C9F2`/`#3B76B8`)과 각자 눈금. 눈금 상한(`DiskActivityScale`) = 60초 창 최고값 이상의 1·2·5 단계, 최소 1 MB/s, 라벨은 "눈금 상한 N MB/s"(측정 최고값이 아님). 창의 최고값으로만 정해져 최고점이 들어오거나 나갈 때만 바뀐다. 곡선·공백 규칙은 Aurora(`AuroraCurve`, `AuroraGraphLayout`, M1 2.5초) 재사용, 값은 눈금 대비 %로 바꿔 넘긴다. 데이터가 없으면 "측정 데이터 없음". CPU·RAM·GPU 색은 그대로.

**I/O 대상 장치:** `IOBlockStorageDriver`는 디스크 이미지(가상 장치)마다 하나씩 더 있다(이 Mac에서 3개 중 2개가 "Disk Image"). 그래서 합계를 내면 안 되고, `/` 컨테이너의 물리 저장 장치 하나(이 Mac: disk0, `APFS Physical Store` disk0s2)만 써야 한다. 미리보기 탐침은 내장(`Internal`) 장치만 골랐다. 구현 시 "/ → APFS 물리 저장 장치 → 그 드라이버"로 정확히 찾는 방법을 확정해야 한다. 외장 디스크 I/O는 포함하지 않는다.

**APFS 공간 표시 정책 (제안)**

- "지금 비어 있음" = `volumeAvailableCapacity`(= `statfs` f_bavail = `df`, `diskutil` Container Free). 아무것도 지우지 않은 지금의 빈 공간.
- "사용 가능" = `volumeAvailableCapacityForImportantUsage`. macOS가 필요할 때 비울 수 있는 공간(삭제 가능 캐시, 로컬 스냅샷 등 purgeable)을 포함할 수 있는 **시스템 추정치**. 시스템 설정 > 저장 공간과 가깝다(§3 V6).
- 차이("필요 시 확보 가능, 추정")는 정확한 purgeable 총량이 아니다. 이름과 도움말에 "추정"을 붙이고, 줄무늬로 확정 값과 구분한다.
- 사용률·"사용 중" = 전체 − 사용 가능(시스템 설정 기준, 메뉴 막대 %와 같은 값). 보수적 사용량(전체 − 지금 비어 있음)은 따로 숫자로 내세우지 않고 막대의 "사용 중 + 확보 가능" 길이로 드러난다.
- APFS 컨테이너의 볼륨들(Macintosh HD, Data, Preboot, VM 등)은 공간을 공유하므로 "볼륨 하나의 사용량"이 아니라 **컨테이너 전체**를 본다. `df /`의 Used(봉인된 시스템 볼륨만, 이 Mac 13.7 GB)를 쓰면 크게 틀린다.
- 로컬 스냅샷(Time Machine)은 지워지기 전까지 공간을 차지하며 보통 purgeable로 취급된다. 이 Mac에는 `/`의 로컬 스냅샷이 없었다(`tmutil listlocalsnapshots /`).
- Finder·시스템 설정과 차이가 나는 이유: 읽은 시점(시스템 설정은 캐시된 계산), 반올림, 10진 단위(GB = 10⁹), purgeable 포함 여부. 앱은 10진 단위로 표시한다.

- **수집 주기:** 바꾸지 않았다. Battery 위젯이 켜져 있는 동안 전원 변경 알림 + 60초 보조 읽기. 한 번에 전원 상태 + 어댑터 + 레지스트리 + 팩 자식을 메인 액터에서 읽는다(측정 프로그램 0.372 ms/회). 새 타이머·팝오버 전용 읽기 없음. 끄면 값과 `batteryReadDate`를 지운다.
- **테스트 (`BatteryPopoverTests` 9개 + `BatterySamplerTests` 실기기 온도 기대값 갱신):** 상태 분류(20% 경계, 충전 중 + 낮음, 연결 + 낮음, 확인 불가, 배터리 없음), 메뉴 막대 값 일치, 시간(정상·계산 중·누락·음수·센티널·상태 불일치), 전원 줄·W(누락·0·이름 무시·미연결 시 없음), 사이클·최대 용량 경계, 온도(변환·실패·120초·시계 역행·비정상·키 없음), 저장소(읽을 때마다 시각 기록, 새 타이머 없음, 중복 없음, 끄면 정리), 이 Mac 실측(10~60 °C, 0.1 K 해석이 아님).

### 7.8 그래프의 측정 실패 구간

- `SystemMetricHistory`의 `nil`은 측정 불가 구간이다. 0%로 그리거나, 앞뒤 유효 점을 선으로 잇지 않는다.
- 표시 계층에서 기록을 **연속된 유효 구간들**로 나누고(순수 함수), Swift Charts에서 구간마다 별도 계열(series)의 선을 그린다.
  - **시간 공백도 끊는다 (6-4a, M1 해결 2026-10-28):** 이웃한 유효 점 사이가 `chartMaxGap` 2.5초(1초 주기 × 2.5)를 넘으면 새 구간을 시작한다. 정확히 2.5초는 잇는다. 잠자기·타이머 정지·GPU 오래된 창 폐기처럼 `nil` 없이 시간만 비는 경우를 위한 것이다. `segments(history, maxGap:)`로 기준을 바꿀 수 있고 기본값은 2.5초다. CPU·RAM·GPU 기록이 같은 함수를 쓴다. 측정 엔진과 기록 정책은 바꾸지 않았다.
  - 점이 하나뿐인 구간은 점으로 표시한다.
  - X축은 최근 60초, Y축은 0~100이다.
- 모든 값이 `nil`이면 그래프 대신 "측정 데이터 없음"을 표시한다.
- 테스트(6-1, 순수 함수)
  - 정상 데이터가 연속되면 구간 1개
  - 중간에 `nil`이 있으면 구간 2개
  - 시작·끝의 `nil`은 구간에 포함되지 않음
  - 모두 `nil`이면 구간 0개
  - 값 0%는 유효한 점으로 남고, `nil`과 구분됨
  - (6-4a 추가) 1초×5 → 20초 공백 → 1초×3은 구간 2개, 2.4·2.5초는 이어지고 2.6초는 끊김, `nil`과 긴 공백이 겹쳐도 빈 구간 없음, 긴 공백 사이 점 하나는 1점 구간, 타이머 흔들림(1.0~1.1초)과 한 번 건너뜀(약 2초)은 이어짐, 원본 기록 불변

### 7.9-1 6-3 연결 구조 (구현)

- `TokenlyApp`은 `SystemWidgetController` **하나만** `@StateObject`로 관찰한다(토글·지원 변경 때만 게시). `SystemMonitorStore`·`ProcessTopStore`는 앱 init에서 만들어 컨트롤러가 보관한다(`controller.store`, `controller.processTop`).
  - 이유: Store를 앱의 `@StateObject`로 두면 1초 게시마다 앱 `body`(AI 메뉴 막대 라벨 포함)가 다시 계산된다.
- Store를 관찰하는 것은 각 `SystemWidgetLabel`뿐이다. 라벨은 `SystemWidgetImageCache`에서 위젯별로 `(표시값, 명암, 배율)`이 바뀔 때만 이미지를 다시 만든다. 배율은 `displayScale`이고 최소 2배로, AI와 같다. 이미지는 non-template이다.
- 설정 "시스템" 탭은 토글 5개를 `controller.binding(for:)`에 연결하고, 미지원이면 토글을 비활성화하고 사유를 표시한다.
- **배터리 표시 스타일 (6-3 최종):** `SystemWidgetController.batteryFrame`(UserDefaults `systemWidget.batteryFrame` = `minimal`/`rounded`, 없거나 모르는 값이면 `minimal`), `batteryFrameBinding()`·`setBatteryFrame(_:)`(저장·게시만). 설정 > 테마의 `BatteryFramePicker`(가로 라디오). 캐시 키에 위젯별로 해석한 테두리(`applied(to:)`)가 들어가 전환 시 Battery만 다시 그린다.
- **표시 방식 (6-3 후속):** `SystemWidgetController.layout`(`@Published`, UserDefaults `systemWidget.layout` = `unified`/`split`, 값이 없거나 모르는 값이면 `unified`). 설정 > 테마의 `SystemWidgetLayoutPicker`가 `layoutBinding()`으로 바꾼다. `setLayout`은 저장·게시만 하고 `stored`·Store·ProcessTop을 건드리지 않는다.
  - 장면은 컨트롤러 게시로 다시 계산되며 `controller.layout`을 각 `SystemWidgetLabel`에 넘긴다. 이미지 캐시 키에 위젯별로 해석한 방식(`applied(to:)`)이 들어가, 전환 시 CPU·RAM·Disk·GPU만 다시 그리고 Battery 이미지는 재사용한다. 같은 방식이면 다시 그리지 않는다.
  - 탭이 나타날 때마다(설정을 이 탭으로 열거나 이 탭으로 전환할 때) `recheckUnsupportedWidgets()`를 부른다.
  - 모두 지원이면 아무 작업도 하지 않고, 미지원 위젯만 다시 확인한다.
- 메뉴 항목 내용은 6-4 전까지 임시다: 현재 값 문구와 `SettingsLink`("시스템 모니터 설정…")만 있고, 팝오버는 없다.

### 7.10 아직 검증하지 않은 macOS 동작
